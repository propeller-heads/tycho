# Execution: encoders, executors and the router

Rules for `crates/tycho-execution`: the Rust encoders, the Solidity executors and the router. The
executor and caller security checklists, the steps for adding an executor and the build commands
are in `crates/tycho-execution/CLAUDE.md`; several records below point there instead of restating
it.

## Rules

Each rule is a record: its id, which review findings cite; the rule; why it matters; how to spot a
violation in a diff (Spot); the kinds of files it applies to; and the tools that check it, in part
or in full (`.claude/skills/tycho-review/SKILL.md` lists the file kinds).

### charge-on-realized-amount
A percentage charge is computed on the amount it is actually levied on (the realized value left after every deduction taken before it), never on an estimate or quote the caller supplied. Its tests cover realized values above, equal to and below the estimate, with each preceding deduction both on and off.
Why: Charging on the quote overcharges whenever the realized value falls short of it, and undercharges when a preceding deduction is disabled.
Spot: Fee or commission arithmetic that multiplies a caller-supplied `expected`, `quoted` or `estimated` amount; a test whose expected fee is derived from the quote while the actual amount differs.
Applies: rust, rust-test, solidity, solidity-test · look first at lines matching `fee|commission|charge|percent|bps|basis|expected|quote|estimat`
Checked by: ast-grep `charge-on-estimate`; ast-grep `sol-charge-on-estimate`

### solidity-naming-convention
Solidity naming: private/internal state variables prefixed '_', parameters that clash with a state variable suffixed '_', custom errors prefixed with the contract name and a double underscore (Contract__Error).
Why: Consistent naming makes storage access and error provenance obvious at a glance.
Spot: New state variables without '_' when private/internal; errors without the Contract__ prefix; shadowing parameters.
Applies: solidity, solidity-test
Checked by: ast-grep `sol-naming-error-contract-prefix`; ast-grep `sol-naming-private-state-underscore`

### executor-no-amount-handling
Source: `crates/tycho-execution/CLAUDE.md` § Adding a New Executor, step 2
Spot: `swap()` returning amounts; balanceOf before/after in an executor; `amount0Delta`/return values sizing a transfer; `require(amountOut > 0)` or equality checks between `amountIn` and encoded values; `_decodeData(data)` whose result is discarded in `fundsExpectedAddress`/`getTransferData`. `if (msg.value != amountIn) revert` or `if (venue.fee(...) != 0) revert` (or similar asserts on venue pricing configuration) in an executor's swap().
Applies: solidity · look first at lines matching `swap|executor|transfer|amount|balance|require|revert|fee|msg\.value|decode|return`
Checked by: ast-grep `sol-executor-balance-tracking`; ast-grep `sol-executor-swap-returns`; ast-grep `sol-view-helper-discarded-decode`; ast-grep `sol-executor-router-covered-check`

### router-integration-test-layers
Execution integrations ship four test layers: encoder unit tests asserting the exact byte layout per direction as literal hex (ending in write_calldata_to_file), executor Foundry tests, a cross-language decode test, and a TychoRouter integration test whose calldata is generated by the Rust encoder in `tests/protocol_integration_tests.rs` and which asserts user balance deltas and zero router residue.
Why: Each layer catches a different class of Rust/Solidity mismatch; transfer-type, receiver and address-config bugs only surface when the router dispatches through the real executor, so executor-only tests pass while the end-to-end path reverts.
Spot: A new `contracts/test/protocols/<Proto>.t.sol` without a `TychoRouterTestSetup`-based test using `loadCallDataFromFile`; no matching entry in `protocol_integration_tests.rs`; encoder tests comparing against bytes built with the encoder's own helpers.
Applies: solidity, solidity-test, rust, rust-test · look first at lines matching `executor|encoder|swap|protocol|calldata|integration`
Checked by: ast-grep `rust-encoder-test-no-literal-bytes`; repo-script `router-integration-test-layers`

### security-model-executor-set
Source: `crates/tycho-execution/CLAUDE.md` § Adding a New Executor, step 8
Spot: A new executor reading the target address from swap data without a model change; executor PRs changing `getTransferData`/`fundsExpectedAddress` without touching the model; an executor with a fixed/allowlisted target added to the `Executor` enum.
Applies: solidity, rust · look first at lines matching `executor|getTransferData|fundsExpectedAddress|target|variant`
Checked by: pr-script `security-model-executor-set`

### executor-address-config
Executor address config entries use the exact protocol-system key and the protocol's own executor address; an address is shared only when the protocol is genuinely executed by that executor, and the encoder registry says so.
Why: A copied address or misspelled key routes the protocol to the wrong executor (or none), and tests at executor level do not catch it.
Spot: New lines in `executor_addresses.json` / `test_executor_addresses.json` whose address duplicates another protocol's, or whose key differs from the protocol system string (e.g. missing `rfq:` prefix).
Applies: config · look first at lines matching `0x|executor|rfq`
Checked by: repo-script `protocol-system-registry`

### executor-chains-match-venue
An executor's (and integration's) configured chains match the chains the venue actually supports, and handling for chains no longer supported is removed.
Why: Deployments or zero-address branches for unsupported chains are dead config that misleads integrators and keeps dead code paths in audited contracts.
Spot: `executor_deployments.json`/`executor_addresses.json` entries for chains absent from the venue's own chain list; constructor branches that tolerate `address(0)` for one chain.
Applies: config, solidity, rust, script
Checked by: ast-grep `sol-constructor-zero-address-sentinel`

### encoder-test-naming
Encoder tests (gas estimator etc.) are named after the transfer characteristic they exercise, consistent with sibling tests and accurate for that transfer type, and they spell out how an expected gas figure decomposes.
Why: Protocol-named tests hide which code path is covered, and an undecomposed gas number cannot be reviewed.
Spot: `fn test_<protocol>_...` among characteristic-named siblings; qualifiers like "optimizable" on a transfer type they don't apply to; bare gas literals without a breakdown.
Applies: rust-test · look first at lines matching `fn test|gas|#\[test\]`

### executor-tests-real-quotes
Executor fork tests run against recorded real quotes/state rather than `vm.etch` mocks, and tests that do not use the TychoRouter live in their own test contract rather than one inheriting `TychoRouterTestSetup`.
Why: Etched mocks only prove the executor matches the mock's assumptions about the venue; misplaced tests pay the router setup and blur what is being tested.
Spot: `vm.etch` in tests named as integration tests; non-router tests inside a `TychoRouter*IntegrationTest` contract.
Applies: solidity-test · look first at lines matching `etch|TestSetup|IntegrationTest|contract\s`
Checked by: ast-grep `sol-router-setup-non-router-test`; ast-grep `sol-router-test-etch`

### executor-transfer-type-per-hop
An executor's transfer classification matches how the venue ingests tokenIn and is traced through Dispatcher/TransferManager for single, first and later hops (with and without the sequential-transfer optimization): `Transfer` with receiver = pool only for venues that need tokens at the pool before the call (IN_TRANSFER_REQUIRED_PROTOCOLS), `None` for callback venues (CALLBACK_CONSTRAINED_PROTOCOLS), `ProtocolWillDebit` with receiver = the contract that actually consumes the input when the venue pulls or wraps it; each gets a sequential-route test.
Why: Misclassification breaks multi-hop routing in ways single-hop tests do not show: `fundsExpectedAddress == msg.sender` with `TransferType.Transfer` reverts with `Vault__UnexpectedNonZeroCount` or forwards a zero `amountIn` as a later hop.
Spot: A new executor whose `fundsExpectedAddress` returns `msg.sender`/router or an intermediate (wrapper) contract combined with `TransferType.Transfer`; changes to IN_TRANSFER_REQUIRED_PROTOCOLS / CALLBACK_CONSTRAINED_PROTOCOLS or `fundsExpectedAddress` without a sequential test; executor tests covering only single-hop.
Applies: solidity, solidity-test, rust, rust-test · look first at lines matching `transfer|fundsExpectedAddress|callback|PROTOCOLS|hop|sequential|receiver`
Checked by: ast-grep `sol-transfer-to-router-receiver`; pr-script `executor-transfer-type-per-hop`

### allowlisted-targets-reachable
Each allowlisted target in an executor can actually pass the executor's subsequent checks (e.g. it exposes the allowlisted selector); otherwise that target is dead and should be dropped.
Why: An allowlist entry that can never pass gives a false impression of support and dead code in an audited contract.
Spot: An allowlist of target addresses plus a selector check, where one target is a different contract type (vault, registry) than the others.
Applies: solidity · look first at lines matching `allow|target|selector|whitelist`

### push-payment-entrypoint
Executors use the venue's push-payment entrypoint (tokens sent to the venue, then `swap`) rather than pull-payment/allowance variants when available, and reuse an existing generic executor that already targets the same interface (for the standard IPropAMM interface, the PropAMMExecutor) instead of adding a venue-specific one.
Why: Pull-payment adds an extra hop (user -> router -> venue) when the venue leg is first in a route, costing gas, and a bespoke executor duplicates audited code.
Spot: Executors calling `*WithAllowances`/`transferFrom`-based entrypoints; a new executor whose venue implements an interface an existing executor already calls. A new executor .sol under contracts/src/executors calling IPropAMM.swap or an equivalent push-payment swap.
Applies: solidity · look first at lines matching `swap|transfer|allowance|executor|propamm|interface`
Checked by: ast-grep `sol-executor-allowance-entrypoint`; ast-grep `sol-reuse-propamm-executor`

### selector-allowlist
Source: `crates/tycho-execution/CLAUDE.md` § Security › Building Executors (executor checklist)
Spot: Executors calling target.call(data) with data taken from the swap payload and no selector check.
Applies: solidity · look first at lines matching `call|selector|calldata`

### neutral-protocol-min-out
Protocol-level min-out and deadline parameters get neutral values (0 / now), and the router's route-level minAmountOut is the price check; the exception is a venue that caps its output and keeps input it cannot fill, where a neutral min-out lets an oversized input be lost, so that leg passes its own floor. Deadline comparison semantics (>= vs >) are verified on a fork when the venue requires one.
Why: Duplicating slippage checks in the executor only adds revert surface without protecting anything the router does not already.
Spot: Executors or encoders passing a computed minAmountOut or tight deadline to the protocol call; `minAmountOut: 0` (or similar) to a venue whose swap keeps the whole input when it fills only part of it.
Applies: solidity, rust · look first at lines matching `min|deadline|slippage|limit|timestamp`
Checked by: ast-grep `sol-executor-protocol-min-out`

### fixed-addresses-are-immutables
Fixed per-deployment addresses are executor constructor immutables (set via deploy config), not calldata and not Rust constants, and values fixed by the ABI of a selector the executor pins (an argument's byte offset, a word position) are constants in the executor; encoded swap data is packed and holds only what the executor cannot know from its immutables and constants.
Why: Encoding fixed addresses wastes calldata and lets the caller substitute them; Rust constants tie the encoder to one deployment.
Spot: Encoders appending addresses that never vary per deployment; executor reading such addresses from data; hardcoded deployment addresses in Rust. Packed swap data carrying an offset/length for a call whose selector the executor already checks against a single allowed value.
Applies: solidity, rust, config, script · look first at lines matching `address|immutable|constant|const |offset|0x|encode|pack|abi|decode|data`
Checked by: ast-grep `sol-calldata-offset-not-constant`

### regenerate-runtime-bytecode

Spot: A contract change with no change to protocols/testing/fixtures/*.runtime.json; a new executor not listed in test/RuntimeBytecodeFixtures.sol; a fixture edited by hand.
Applies: solidity, solidity-test, integration-test

### encoder-rejects-unsupported
Encoders reject at construction or encode time, with InvalidInput, anything the deployed contract would revert on: an unsupported chain or protocol variant (new() is restricted to supported chains) and every amount precondition the router enforces (non-zero amountIn and expectedAmountOut, 0 \< minAmountOut \<= expectedAmountOut).
Why: An encode-time error is cheap and explicit; an on-chain revert costs gas and hides the cause.
Spot: Encoders with no chain check in new(); variants the deployed contract does not support passed through to calldata. A new or changed `revert` on amount parameters in TychoRouter with no matching check in `validate_solution`.
Applies: rust, solidity · look first at lines matching `chain|fn new|revert|amount|variant|protocol|invalidinput|encode|validate|match`
Checked by: ast-grep `rust-encoder-new-ignores-chain`

### fork-test-block-and-inventory
Fork tests pick a block where the swap is actually executable (for freshness-gated venues, a block containing a state commit) and fund/approve external inventory with deal + prank rather than relying on live balances at that block.
Why: Live values at a fork block are not stable fixtures, and a block without fresh state makes the test prove the revert path only.
Spot: Fork tests depending on a maker's live balance/allowance; fork blocks chosen without regard to venue state updates.
Applies: solidity-test, rust-test · look first at lines matching `fork|block|deal|prank|balance|approve|vm\.`

### router-test-setup-addresses
A change to TychoRouterTestSetup's deployment sequence re-derives the deterministic test executor addresses, regenerates calldata.txt, and re-runs at least one pre-existing router suite; sibling PRs that each append an executor are flagged because they predict the same address.
Why: Test executors deploy at nonce-derived addresses, so an appended deployment shifts everything after it and two PRs collide on merge.
Spot: Changes to TychoRouterTestSetup.sol or test_executor_addresses.json; PRs adding an executor while another open PR does too.
Applies: solidity-test, config
Checked by: pr-script `router-test-setup-addresses`; pr-script `sibling-router-setup-prs`

### bytecode-fixtures-own-chain
Runtime-bytecode fixtures deploy each contract on its own deployment chain at a pinned block, and any per-fixture override may change only the block, not the chain.
Why: A constructor that reads chain state bakes the forked chain's values into immutables, so a Base executor built on a mainnet fork silently differs from its deployment.
Spot: A default fork (`mainnet`) applied to all fixtures, or an override helper taking a free `chain` argument.
Applies: solidity-test, integration-test, script · look first at lines matching `fork|chain|block|mainnet|rpc|fixture`

### reproducible-fixture-addresses
Generated test fixtures must be reproducible from the repo alone: deploy with a dedicated fresh key, `anvil_setNonce`, or (for fixtures deployed on chain) CREATE2/CREATE3 salts, never from a publicly known key whose mainnet nonce third parties change, and never with addresses depending on fixture order. A helper that needs the same address under `forge test` and `forge script` uses `deployCodeTo` at a name-derived address (`deterministic-address-test-and-script`).
Why: Fixtures baking `address(this)` then depend on a fork block and list position; inserting a fixture rewrites unrelated ones and the pinned block can never move.
Spot: Fixture/bytecode scripts using anvil account #0 (0xac0974…) on a mainnet fork with CREATE; sequential deploys in one anvil instance.
Applies: solidity-test, integration-test, script, rust-test · look first at lines matching `deploy|key|nonce|create|salt|anvil|0xac09|fixture|prank|address`
Checked by: repo-script `public-deployer-key`

### opt-in-test-overrides
Test-only state overrides that paper over deployment gaps (e.g. executor activation timelocks) must be opt-in, so a missing on-chain step still surfaces as a revert by default.
Why: Always-on overrides make tests pass against a configuration that does not exist on chain.
Spot: Unconditional router/executor bytecode or storage overrides in integration tests.
Applies: solidity-test, rust-test, integration-test · look first at lines matching `etch|store|override|setcode|setstorage|timelock|bytecode|state`

### no-placeholder-addresses
Config files and contract constants never ship placeholder or zero addresses: deployment args carry the real per-chain address for every listed chain, and a 'TODO: replace with deployed address' constant is replaced before merge or tracked on the deployment task.
Why: A zero or placeholder address encodes calldata that reverts or approves nothing, and a forgotten placeholder ships silently because nothing fails at build time.
Spot: `0x0000000000000000000000000000000000000000` or `0x…_HERE` values in config JSONs, `PLACEHOLDER`/`TODO: replace` next to an address constant, a contributor PR editing executor_addresses.json.
Applies: config, solidity, script, rust · look first at lines matching `0x|placeholder|todo|_here|address`
Checked by: ast-grep `json-placeholder-address`; ast-grep `sol-placeholder-address-constant`

### executor-validates-supplied-addresses
An executor validates on chain every caller-supplied address it approves, transfers to or calls (wrapper tokens, pools) against the protocol's canonical factory or registry, because calldata reaching the router can be hand-crafted and indexer-side filtering does not protect it.
Why: A fake wrapper or pool passed in crafted calldata receives an approval or transfer from the router and drains funds via transferFrom.
Spot: Executor swap()/getTransferData that decodes token or pool addresses from `data` and approves or calls them without a factory lookup (getPair/getWrappedToken/isPool) or equivalent check.
Applies: solidity · look first at lines matching `address|approve|call|decode|pool|token|transfer`

### fork-executor-follows-sibling
An executor for a fork of an already-integrated venue follows the sibling executor's settlement flow (e.g. swap the full credit read back after settle, not the nominal amountIn) and justifies each deviation.
Why: Diverging from a proven flow reintroduces edge cases the sibling already handles, such as a credited amount that differs from the nominal input.
Spot: A new V4-style executor that settles amountIn and then swaps amountIn instead of reading back _getFullCredit like UniswapV4Executor.
Applies: solidity · look first at lines matching `settle|credit|swap|amount|unlock|take|sync|pool`
Checked by: ast-grep `sol-settle-without-credit-readback`

### deployment-artifacts-after-launch
An integration PR leaves deployment-time artifacts untouched: deployed executor addresses (executor_addresses.json) and the solver-facing supported-protocols listing change only after the executor is deployed and the integration is live in production.
Why: Listing an undeployed executor or an unlaunched protocol advertises something solvers and hosted users cannot use yet, and placeholder addresses get mistaken for real deployments.
Spot: An integration diff touching crates/tycho-execution/config/executor_addresses.json or docs/for-solvers/supported-protocols.md.
Applies: config, docs

### executor-receive-justified
A `receive()` on an executor is added only with a stated reason the executor itself receives ETH (direct use, a venue paying the executor address); under the router's delegatecall the router, not the executor, receives ETH.
Why: An unexplained receive() suggests ETH flows that cannot happen and invites stuck-funds questions in audits.
Spot: `receive() external payable {}` in a new executor without a comment naming who sends ETH to it.
Applies: solidity · look first at lines matching `receive|payable`
Checked by: ast-grep `sol-executor-receive-unexplained`

### rust-model-mirrors-contract
The Rust model of a contract (router, dispatcher, fee calculator, executors) mirrors the contract's current control flow step by step (the order of checks relative to balance finalisation, helper boundaries, named constants) and changes in the same PR as the contract.
Why: A model that checks in a different order, or keeps a helper the contract has removed, explores states the chain never reaches and misses states it does.
Spot: Contract changes under contracts/src with no matching change in crates/tycho-execution/model; a model check placed before or after a step that the Solidity orders differently; a model constant inlined where the contract has a named one; executor PRs changing `getTransferData`/`fundsExpectedAddress` without touching the model.
Applies: solidity, rust

### security-model-models-the-guard
The security model accepts a family of routes as safe only by modelling the on-chain guard that makes them safe: it requests the input that decides safety (the venue, the pool) and reverts for sender-controlled values the guard rejects. Each new model branch has a unit test.
Why: An unconditional Ok(()) for a whole executor family hides any discrepancy in the router interaction from the fuzzer, and accepts routes that revert on chain.
Spot: A model arm that returns Ok(()) after requesting only the token slices; a model change with no #[test]; a reachable revert branch that no test covers.
Applies: rust, rust-test
Checked by: ast-grep `rust-model-arm-unconditional-ok`

### router-claims-tested-through-router
When a PR's central claim concerns router behaviour around an executor (approvals, balance-diff accounting, a mid-route receiver, fees), or the executor's funding or receiver can vary, that behaviour is exercised through TychoRouter and Dispatcher for a single swap, a split swap (a fraction of the input transferred), the executor as a non-first sequential hop (funded only by the previous hop's output), a route with a client/router fee (receiver redirected to the router), and a minAmountOut-binding swap; executor-level tests alone do not cover it.
Why: Dealing tokens to the executor and calling swap() directly bypasses the Dispatcher's transfer, approval, revoke and balance-diff machinery, which is where the new integration can break.
Spot: New executor tests that `deal` tokens to the executor and call `executor.swap()` directly, with no test contract inheriting TychoRouterTestSetup for that executor. Executor router tests that all use noClientFee() and only singleSwap or first-hop sequentialSwap.
Applies: solidity, solidity-test · look first at lines matching `swap|executor|router|deal|approve|fee|receiver`

### wire-enum-ordinals-pinned
Test builders produce enum-coded wire bytes by casting the contract's enum (`uint8(Contract.Enum.Variant)`), and a separate test pins every ordinal to its documented literal byte, since the ordinals are the wire format another language emits.
Why: Literal ordinals in builders let an enum reorder silently repoint tests at a different variant, while casting alone lets tests follow a reorder that breaks the off-chain encoder.
Spot: `uint8(0)`..`uint8(4)` literals in test helpers next to a contract enum dispatched on the same byte.
Applies: solidity-test, solidity · look first at lines matching `uint8|enum`
Checked by: ast-grep `sol-test-literal-enum-ordinal`

### re-transfer-outside-balance-diff
A contract that receives tokens from the router and then makes its own transfer to the venue is outside the Dispatcher's balance measurement, so it either trades the amount the venue actually received or documents fee-on-transfer and rebasing input tokens as unsupported, and docs claiming universal support for them name the exception.
Why: The second transfer loses another cut, the leg is priced on the full amount, and the venue reverts (K check, IIA, CurrencyNotSettled) with an error that says nothing about the token.
Spot: An intermediate contract doing `safeTransfer(venue, amountIn)` with amountIn taken from the router's call rather than a balance or credit read.
Applies: solidity, docs · look first at lines matching `transfer|fee-on-transfer|rebas|amountin`
Checked by: ast-grep `sol-retransfer-nominal-amount`

### per-chain-support-table
When what an encoder can encode depends on the chain, the per-chain support set lives in one table that the encoder enforces at encode time, that consumers can query (a public predicate or constant), and that tests check against the executor and deployment configs.
Why: Without one queryable table, a solver routes to a protocol the chain's contract cannot run and learns it from an on-chain revert.
Spot: A chain-dependent encoder with only a `chain != Chain::X` gate, or support derived ad hoc from config files at encode time.
Applies: rust, rust-test · look first at lines matching `chain`
Checked by: ast-grep `rust-encode-time-chain-gate`

### fork-aliases-in-encoder
An encoder that takes a protocol name from user data accepts every fork that runs through the same executed interface as an alias of the family variant (with its fork-specific parameters, such as a fee), and lists only forks deployed on chains the encoder supports.
Why: A solver naming a fork (sushiswap_v2) is rejected even though the family's code path executes it, or a fork on an unsupported chain is accepted.
Spot: A serde-tagged protocol enum keyed by family names only, beside an executor_addresses.json that lists fork protocol systems.
Applies: rust, config · look first at lines matching `serde|protocol|alias|rename|fork|enum|variant|0x`

### deployed-copy-may-stay-duplicated
A second copy of a stable venue integration inside a new contract may stay duplicated when extracting it would change already-deployed executor code, provided the copy's known divergences are documented at the copy and a test pins any shared wire format.
Why: Forcing extraction into a shared library changes deployed executors' bytecode and revert behaviour in a PR about something else.
Spot: A review asking to extract shared venue code where the other caller is a deployed executor.
Applies: solidity

### auxiliary-step-never-reverts-swap
An auxiliary on-chain step that runs inside a user's swap transaction (a subsidy payment, a reward) never reverts the swap: every failure, including being paused, an invalid signature or a failed transfer, skips that step with a recorded reason.
Why: A revert in the auxiliary step (e.g. a whenNotPaused modifier) takes down every swap that touches it when the side system is paused or misconfigured.
Spot: `whenNotPaused`, `require` or a reverting transfer helper (`Address.sendValue`) in a hook the router calls after a hop.
Applies: solidity · look first at lines matching `paus|require|revert|send|transfer|hook|subsidy|reward|signature|try|catch`
Checked by: ast-grep `sol-auxiliary-hook-can-revert`

### solution-gas-covers-every-step
A solution-level gas estimate covers every step the transaction executes: each swap's simulated gas plus router overhead, the user's input and output transfers, approvals, and any step the encoder inserts (wrap/unwrap bridges), each term following the transfer path the router takes for that strategy and hop position and costed per direction where costs differ; its tests use the strategy the encoder would assign to the solution.
Why: A per-swap sum understates the transaction's gas, and solvers that rank or price routes on it pick routes that cost more than they report.
Spot: Docs or code calling the sum of `estimated_gas` over swaps the solution's gas, an encoder-inserted step with no gas entry, or one gas constant used for both directions of an asymmetric operation.
Applies: rust, rust-test, docs · look first at lines matching `gas`

### callback-validates-caller-and-request
Source: `crates/tycho-execution/CLAUDE.md` § Security › Building Executors (executor checklist)
